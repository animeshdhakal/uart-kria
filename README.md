# UART on AMD Xilinx Kria K26 SOM (KV260 / KR260)

This is a synthesizable SystemVerilog implementation of the UART protocol (8N1) targeted for the **AMD Xilinx Kria K26 SOM** (KV260 Vision AI Starter Kit / KR260 Robotics Starter Kit). It includes both RX and TX modules, a top-level character streamer, and a complete hardware wrapper configured with the Zynq UltraScale+ MPSoC Processing System (PS).

All simulation testbenches use cocotb and Verilator. The Vivado implementation flow follows a clean TCL-first approach driven via CLI.

---

## Architecture

On the Kria K26 SOM (KV260 / KR260), there is no dedicated external PL oscillator connected directly to fabric pins. The PL clock is generated by the Zynq UltraScale+ MPSoC Processing System (PS) and delivered to the fabric. See [Clocking](#clocking) for the full chain and its boot-time implications.

- `rtl/uart_tx.sv` — Transmitter module (8N1 framing, configurable baud rate).
- `rtl/uart_rx.sv` — Receiver module with 2-stage input synchronizer.
- `rtl/top.sv` — Pure RTL UART module that repeatedly transmits `"Animesh"` every 1 second over UART TX. Tested directly in cocotb.
- `rtl/kria_top.sv` — Hardware top-level for Kria K26 SOM. Connects the Zynq MPSoC PS clock (`pl_clk0` = 100 MHz) and reset (`pl_resetn0`) to `top.sv`, routing `uart_tx` to PMOD Pin 1.
- `scripts/create_bd.tcl` — Generates the Vivado Block Design (`system.bd`) with the `zynq_ultra_ps_e` IP configured with official Kria board presets.

## Clocking

The clock **is** connected to the Zynq UltraScale+ — the PS is its source. What the design does not use is a separate oscillator wired directly to a PL (fabric) pin.

The Zynq UltraScale+ has two parts:

```
┌──────────────────────── Zynq UltraScale+ ────────────────────────┐
│                                                                  │
│  PS (Processing System)                 PL (Programmable Logic)  │
│  ┌──────────────────────┐               ┌─────────────────────┐  │
│  │ ARM cores, PLLs,     │  pl_clk0      │                     │  │
│  │ DDR, peripherals     │ ────────────► │  UART logic         │  │
│  │                      │  pl_resetn0   │                     │  │
│  └──────────▲───────────┘ ────────────► └─────────────────────┘  │
│             │                                                    │
└─────────────┼────────────────────────────────────────────────────┘
              │ PS_REF_CLK (from SOM oscillator)
        33.33 MHz
```

- The **PS** is clocked from a reference oscillator on the K26 SOM. That oscillator connects to dedicated PS clock pins, not to fabric pins. Per the Kria K26 SOM Data Sheet (DS987), `PS_REF_CLK` is connected to a 33.33 MHz oscillator.
- The PS contains the PLLs and clock dividers.
- One of its outputs is `pl_clk0`, a clock intended for the **PL**.
- `pl_resetn0` is the corresponding active-low reset for the PL.

The complete chain is:

```
SOM oscillator → PS_REF_CLK → PS PLLs → PL0 divider → pl_clk0 (100 MHz)
    → BUFG_PS → kria_top → UART logic
```

### Where it is configured

[scripts/create_bd.tcl](scripts/create_bd.tcl) instantiates `zynq_ultra_ps_e` (the PS), applies the Kria board preset, enables PL fabric clock 0 at 100 MHz, and exports the clock and reset:

```tcl
CONFIG.PSU__FPGA_PL0_ENABLE {1}
CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100}
```

```tcl
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0]    $clk_port
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_resetn0] $rst_port
```

These become ports of the generated `system_wrapper`, which [rtl/kria_top.sv](rtl/kria_top.sv) instantiates:

```systemverilog
system_wrapper u_system(
    .pl_clk0(pl_clk0),
    .pl_resetn0(pl_resetn0)
);
```

`pl_clk0` is therefore an internal wire from the PS block to the UART, not a top-level port. `kria_top` has only `uart_tx` as an external port, which is why [constraints/pins.xdc](constraints/pins.xdc) contains no `create_clock`. Vivado derives the 10 ns constraint from the PS IP; the routed timing report confirms `clk_pl_0` at 100 MHz.

### From 100 MHz to UART timing

Both UART modules use the clock as a timebase rather than as a data clock:

```systemverilog
localparam int CLKS_PER_BIT = CLK_FREQUENCY / BAUD_RATE;
```

At 100 MHz and 115200 baud:

```
CLKS_PER_BIT = 100_000_000 / 115_200 = 868 (integer)
actual baud  = 100_000_000 / 868    = 115,207.4 Bd
error        = +0.0064 %
```

The TX state machine holds each bit for 868 clock cycles. The RX waits half a bit (434 cycles) to sample the middle of the start bit, then every 868 cycles afterwards.

The one-second message interval also comes from the clock:

```systemverilog
DELAY_CYCLES = 100_000_000   // 1 s at 100 MHz
```

`top.sv` counts that many cycles in `IDLE_WAIT`. The actual cadence is slightly longer than 1 s because the seven-character message takes 7 × 10 bits × 8.68 µs ≈ 608 µs, so the message repeats every ~1.0006 s.

### Changing the clock frequency

The `CLK_FREQUENCY` parameter must match the actual `pl_clk0` frequency. If the PL0 frequency is changed in the block design, update `CLK_FREQUENCY` in `rtl/kria_top.sv` as well; otherwise the baud rate and delay scale incorrectly (half the clock gives half the baud rate and a 2 s delay).

### Boot-time behavior

The PS half of the block design is **not** configured by the `.bit` / `.bit.bin`. The bitstream only configures the PL. The PS clock setup is applied at boot by the Kria firmware (the `psu_init` code inside `BOOT.BIN`). The stock Kria Linux image already provides `pl_clk0` at 100 MHz, which is why loading just the bitstream with `fpgautil` works.

If the PL0 frequency is changed in the block design and only the bitstream is reloaded, the fabric still receives whatever the running firmware configured, not the new frequency. Changing PS clocks requires updating the boot image / device tree, not just the bitstream.

## Hardware Pinout & Wiring

The UART TX signal is mapped to package pin `H12` (Bank 45, 3.3V LVCMOS) in [constraints/pins.xdc](file:///Users/animesh/Developer/uart/constraints/pins.xdc):

- **KV260**: PMOD Connector **J2 Pin 1**
- **KR260**: PMOD Connector **3 Pin 1**

### Connecting to a USB-to-UART Adapter (e.g., CP2102, FT232, CH340)

| KV260 PMOD J2 Pin | FPGA Pin | Signal / Function | Connect to USB-UART Adapter |
| :---: | :---: | :---: | :---: |
| **Pin 1** (Top-Left) | `H12` | `uart_tx` (FPGA TX output) | **RXD** (Adapter RX input) |
| **Pin 9** or **10** | GND | Ground | **GND** |

> [!NOTE]
> Serial terminal settings: **115200 baud, 8 data bits, no parity, 1 stop bit (8N1)**.

## Hardware Build (Vivado CLI)

The project and bitstream creation is fully automated via TCL:

```sh
# 1. Create the Vivado project and block design
make project

# 2. Run synthesis, implementation, write bitstream and generate .bit.bin
make build
```

This generates:
- `build/vivado/uart.runs/impl_1/kria_top.bit` — Standard FPGA bitstream for Vivado Hardware Manager / JTAG.
- `build/vivado/uart.runs/impl_1/kria_top.bit.bin` — Binary bitstream ready for Kria Linux (`fpgautil` / `xmutil`).

## Loading Bitstream onto Hardware

### Option A: Via Vivado Hardware Manager (JTAG)
1. Connect the micro-USB cable from your host to the KV260/KR260 JTAG/UART port.
2. In Vivado Hardware Manager, connect to target and program the device with `kria_top.bit`.

### Option B: On running Kria Linux (Ubuntu / PetaLinux)
1. Copy `kria_top.bit.bin` to the target board:
   ```sh
   scp build/vivado/uart.runs/impl_1/kria_top.bit.bin root@<kria-ip>:/tmp/
   ```
2. On the Kria board, load the bitstream into the PL:
   ```sh
   fpgautil -b /tmp/kria_top.bit.bin
   ```
3. Open a serial terminal on your host connected to the PMOD USB-UART adapter:
   ```sh
   picocom -b 115200 /dev/ttyUSB0
   ```
   You will see `Animesh` printed once every second.
